Status: **navigation map for the Core Sketch product-definition system**

## Canonical work order

For any broad Masck One product task, read in this order:

1. `CORE_SKETCH_START_HERE.md` — canonical entry point and current execution rule.
2. `PRODUCT_CONCEPT.md` — highest-level whole-routine thesis, boundaries and portability definition.
3. `CORE_SKETCH_ONE_PAGE.md` — one-minute product invariant test.
4. `CORE_SKETCH_V1.md` — full selected product/UX/industrial-design specification.
5. `CORE_SKETCH_CONVERGENCE_REVIEW.md` — whole-product contradictions, surviving architecture, proof gates and kill/pivot conditions.
6. `CORE_SKETCH_P0_FEASIBILITY_CONTRACTS.md` — canonical execution meaning for CS-015..018 and the joint resource/product-integrity invariants.
7. `CORE_SKETCH_CONTACT_OCCLUSION_MATRIX.md` — phase-by-phase all-contact support/shadow contract.
8. `CORE_SKETCH_ROUTINE_RESOURCE_ENVELOPE.md` — single whole-routine fluid/mass/CG/torque/energy/time/dock ledger.
9. `CORE_SKETCH_REDUCED_REGION_PROOF_PACKAGE.md` — first BENCH proof program and promotion gates RR-1..RR-5.
10. `CORE_SKETCH_P0_OWNER_TRIAGE.md` — dated exact-head CI/ownership classification; live GitHub wins when owners move.
11. `CORE_SKETCH_FIVE_LANE_EXECUTION_PLAN.md` — five top-level missions and routing of previous subsystem-centric tasks.
12. `CORE_SKETCH_STATUS_BOARD.md` — compact view of current G0..G5 proof gates.
13. `CORE_SKETCH_EXECUTION_BACKLOG.md` — canonical CS IDs, dependency-ordered product-wide to-do list and detailed acceptance.
14. `CORE_SKETCH_REPO_MAPPING.md` — maps work to established owner lineages and genuinely new owner areas.
15. the relevant subsystem engineering documents, live machine/brand authority, current owner PR/branch and accepted exact-head evidence.

Do not start implementation from the research archive. Research records exploration; it does not select product truth.

## P0 feasibility execution layer

These files translate the Core Sketch from a selected concept into falsifiable product contracts:

- `CORE_SKETCH_P0_FEASIBILITY_CONTRACTS.md` — required-region completion, all-contact transition, prepared-session validity, product preservation/carryover, resource closure and pivot rules.
- `contracts/core_sketch_p0_convergence_v1.json` — machine-readable non-authoritative form of the logical P0 invariants.
- `../tests/test_core_sketch_p0_convergence_contract.py` — hostile tests that prevent concept/evidence loopholes; these tests do not prove physical performance.
- `CORE_SKETCH_CONTACT_OCCLUSION_MATRIX.md` — current functional contact-state matrix; future exact source-bound shadow maps must refine it.
- `CORE_SKETCH_ROUTINE_RESOURCE_ENVELOPE.md` — S0 minimum, S1 normal-PM and S2 demanding-AM resource scenarios; unknown inputs cannot be silently zero-filled.
- `CORE_SKETCH_REDUCED_REGION_PROOF_PACKAGE.md` — smallest useful physical sequence proof before whole-face expansion.
- `CORE_SKETCH_P0_OWNER_TRIAGE.md` — records whether current owner heads are green, red, cancelled or have no exact-head receipt, and keeps fixes in canonical lineages.

CS-015 through CS-018 remain the canonical backlog IDs. These execution files elaborate them; they do not create parallel backlog items.

## Truth hierarchy

The Core Sketch describes the selected target product and how work should converge toward it. It does not override live engineering truth.

When statements conflict, use this order for claims about what physically exists or works:

1. released machine engineering authority and schemas;
2. accepted exact-head source/CAD/evidence;
3. released subsystem engineering documents;
4. Core Sketch selected product intent and P0 execution contracts;
5. research archive and historical exploration.

A concept target may deliberately demand future engineering change, but that conflict must remain explicit until the engineering is changed and revalidated.
